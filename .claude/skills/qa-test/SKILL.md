# QA Test Skill

## 트리거

다음 표현에서 활성화:
- "테스트해줘" (dev-test와 구분: 기능/UI 검수 맥락이면 이 스킬)
- "QA 해줘", "검수해줘"
- "점검해줘", "전체 점검"
- "QA 문서 만들어줘"
- 개발 완료 후 "확인해줘"

### dev-test vs qa-test 구분

| 상황 | 스킬 |
|------|------|
| "빌드 테스트해줘", "린트 돌려줘" | dev-test |
| "브라우저 테스트해줘" | dev-test-browser |
| "기능 테스트해줘", "전체 점검해줘", "QA해줘" | **qa-test** (이 스킬) |
| 개발 완료 후 "테스트해줘" | **qa-test** (이 스킬) |

---

## 개요

> QA = 문서 기준으로 실제 구현을 교차 검증하고, 이슈를 찾아 수정하고, 결과를 기록한다.

```
QA 워크플로우:
1. 기준 문서 파악 (PRD, REF, TECHSPEC)
2. 실제 구현 점검 (코드 + 배포 번들 + 라이브 사이트)
3. 이슈 발견 → 기록
4. 수정 → 재검증
5. QA 문서 생성/업데이트
6. 문서 공유 (GitHub + MarkdownBlog)
```

---

## 실행 단계

### Step 1: 범위 결정

사용자 요청에서 QA 범위를 파악한다:

| 범위 | 예시 | 점검 대상 |
|------|------|----------|
| **단일 기능** | "네비게이션 테스트해줘" | 특정 기능의 전 프로젝트 교차 검증 |
| **단일 프로젝트** | "community 테스트해줘" | 해당 프로젝트 전체 기능 |
| **전체 플랫폼** | "전체 점검해줘" | 모든 프로젝트 주요 기능 |
| **PRD 기반** | "PRD 기준으로 테스트해줘" | PRD 마일스톤 항목별 검증 |

### Step 2: 기준 문서 수집

점검 기준이 되는 문서를 찾는다:

```bash
# 해당 프로젝트의 docs/ 폴더에서 기준 문서 찾기
ls {프로젝트}/docs/REF_*.md      # 레퍼런스 (구현 기준)
ls {프로젝트}/docs/plan/PRD_*.md  # PRD (기능 요구사항)
ls {프로젝트}/docs/TECHSPEC_*.md  # 기술 설계 (아키텍처 기준)
```

기준 문서가 없으면:
- 코드에서 기능 목록 추출
- CLAUDE.md에서 프로젝트 스펙 확인

### Step 3: 점검 항목 생성

기준 문서에서 **검증 가능한 항목**을 추출한다:

```markdown
## 점검 기준

| # | 항목 | 기준 | 검증 방법 |
|---|------|------|----------|
| 1 | {항목명} | {문서 §N 기준} | 코드 확인 / 번들 검증 / API 테스트 |
| 2 | ... | ... | ... |
```

### Step 4: 프로젝트별 점검 실행

서브에이전트를 활용하여 **병렬로** 점검한다:

```
복잡도 3+ → 서브에이전트 병렬 점검
복잡도 1~2 → 직접 점검
```

점검 방법:

| 방법 | 용도 | 도구 |
|------|------|------|
| **코드 분석** | 소스 코드가 기준에 맞는지 | Grep, Read |
| **번들 검증** | 배포된 빌드에 반영됐는지 | Bash (grep 번들) |
| **API 테스트** | 엔드포인트 응답 확인 | Bash (curl) |
| **라이브 사이트** | 실제 사이트 동작 확인 | WebFetch, Bash |
| **DB 검증** | 데이터 정합성 | Bash (node + sqlite) |

### Step 5: QA 문서 생성

점검 결과를 문서로 생성한다:

**파일명**: `{프로젝트}/docs/QA_{기능명}.md`
**접두어**: `QA_` (Dev Hub 자동 동기화 대상)

```markdown
# {기능명} QA 점검 보고서

> 기준 문서: `docs/{REF|PRD|TECHSPEC}_xxx.md`
> 점검일: YYYY-MM-DD
> 상태: {✅ 완료 | 🔄 진행 중 | 🔴 이슈 발견}

---

## 점검 기준 요약

| # | 항목 | 기준 |
|---|------|------|
| A | {항목} | {기준 설명} |
| B | ... | ... |

---

## 전체 요약

| # | 프로젝트 | 상태 | A | B | C | ... | 수정 필요 |
|---|----------|:----:|:-:|:-:|:-:|:---:|:---------:|
| 1 | {프로젝트} | ✅/🔴 | ✅ | 🔴 | ✅ | ... | {내용} |

---

## 프로젝트별 상세

### 1. {프로젝트명} {✅/🔴}

| 항목 | 결과 | 비고 |
|------|:----:|------|
| A. {항목} | ✅/🔴 | {상세} |

---

## 발견된 이슈

| 우선순위 | 이슈 | 영향 | 상태 |
|:-------:|------|------|:----:|
| P1 | {이슈} | {영향} | ✅ 수정됨 / 🔴 미수정 |

---

## 수정 완료 내역

| Phase | 내용 | 상태 |
|:-----:|------|:----:|
| 1 | {수정 내용} | ✅ |

---

## 변경 이력

| 시간 | 내용 |
|------|------|
| HH:MM | {내용} |
```

### Step 6: 이슈 수정 + 재검증

이슈 발견 시:
1. 수정 코드 작성
2. 커밋+푸시
3. 배포 확인 (번들 검증)
4. QA 문서 업데이트 (🔴 → ✅)
5. 반복

### Step 7: 문서 공유

QA 완료 후 `doc-view` 규칙에 따라 공유:

```
📄 QA 점검 완료

- **GitHub**: https://github.com/feelgame3025/{repo}/blob/main/docs/QA_{기능명}.md
- **MarkdownBlog**: https://markdown.ilouli.com/project/{project}/{docId}
```

## 점검 유형별 체크리스트

### 기능 교차 검증 (NavigationBar 등 공유 기능)

```
- [ ] 기준 문서 확인 (REF_xxx.md)
- [ ] 전체 프로젝트 소스 코드 점검
- [ ] 배포된 번들에 반영 여부 (grep)
- [ ] i18n 번역 키 존재 여부
- [ ] 아이콘/에셋 존재 여부
- [ ] 빌드 성공 여부
- [ ] 라이브 사이트에서 실제 동작 확인
```

### URL 라우팅 검증

```
- [ ] 모든 섹션에 개별 URL 존재
- [ ] 필터/카테고리가 query param에 반영
- [ ] 뒤로가기/앞으로가기 정상 동작
- [ ] URL 직접 접근 시 올바른 상태 복원
- [ ] 공유 가능한 URL 형태
```

### API 검증

```
- [ ] 엔드포인트 응답 코드 (200/201/4xx)
- [ ] 응답 형식 (success/data/error)
- [ ] 인증 필요 엔드포인트 401 확인
- [ ] 권한 부족 시 403 확인
- [ ] CORS 설정 확인
```

### 배포 검증

```
- [ ] GitHub Actions 빌드 성공
- [ ] 배포된 번들 날짜 확인 (최신인지)
- [ ] PM2 서비스 online 상태
- [ ] 라이브 사이트 접근 가능
```
